## Archive mounting, EaW fallback and Lua loading (answers for the assets stream)

Source: disassembly of the boot function at **0x5d990** (it also sets fonts, registry `Software\Petroglyph`, etc.), `MegaFileManagerClass::Add_Megafile` **0x216b50**, MegaFiles.xml loader **0x217740**, EaW-locator **0x21dce0**.

**(b) EaW GameData fallback - yes.** 0x21dce0 locates the base game and logs `Setting FALLBACK_PATH to %s`: it tries the registry (`Software\LucasArts\Star Wars Empire At War\1.0` -> `ExePath`, checks `Revision`), then `..\..\EAW\Run\` (LaunchSWEAW.bat layout), then **`..\GameData\`** (Steam layout, checks `..\GameData\sweaw.exe`). A `FALLBACKPATH=` command-line switch adds loose-file fallback directories, searched before the EaW one. It does not change FALLBACK_PATH or which EaW MEGs are mounted; see A3. If no EaW install is found FoC aborts with `Unable to locate the installation path of Star Wars: Empire At War...`. The fallback path (global std::string at RVA 0xa15320) is then used to mount EaW's archives first.

**(a) Mount order** (as executed in 0x5d990):

1. if FALLBACK_PATH set: `<EaW>\Data\MegaFiles.xml` (every listed .meg, in file order)
2. `<EaW>\Data\Patch.meg`, `<EaW>\Data\patch2.meg`, `<EaW>\Data\64Patch.meg` (each only if present)
3. `.\Data\MegaFiles.xml` (FoC, in file order)
4. `Data\Patch.meg`, `Data\patch2.meg`, `Data\64Patch.meg` (FoC; hard-coded strings at 0x802db8/0x802dc8/0x802dd8, not in MegaFiles.xml)
5. FALLBACK_PATH is appended as the last loose-file fallback root (call 0x214110), after any `FALLBACKPATH=` directories; see A3.

`Add_Megafile` (corrected 2026-10-26, see PHASE2_ANSWERS Q14):
- It skips a path string that is already mounted (case-insensitive compare, 0x2171c0).
- Otherwise it assigns the archive an incrementing load index and **appends it at the tail** of the archive list. It does not insert at the head.
- The newest-wins behaviour therefore comes from the lookup side: `Open_File` (0x219ff0) presumably walks in reverse or compares load indices. That part has not been re-read statically.

> **Status 2026-10-30:** In-game probe v2 confirmed that the later-listed MEG wins (next bullet; `engine/vfs/include/alamo/vfs/vfs.hpp:10-14`). The reverse walk in `Open_File` itself is still not re-read statically, as `vfs.hpp` also records.

- **Later mounts override earlier ones.** Probe v2 confirmed this at runtime: the later-listed MEG wins.
- The archive is opened through the normal FileClass open with "archive only" off, so a relative `Data\X.meg` goes through the mod search list first. A mod's `Data\Config.meg` therefore replaces the base one, and the base copy is never mounted. Effective priority, highest first: FoC 64Patch > FoC patch2 > FoC Patch > FoC MegaFiles.xml entries (last listed wins) > EaW 64Patch > EaW patch2 > EaW Patch > EaW MegaFiles.xml entries. Loose files on disk (and `MODPATH=`/`STEAMMOD=` mod directories, parsed at 0x67d70; `RELAUNCH MODPATH=Mods/%s`) take precedence over archives in FileClass open; exact loose-vs-meg ordering for the FoC dir vs FALLBACK dir should be confirmed dynamically (one breakpoint on 0x216b50 and on the file-open path). Audio megs (`SFX2D_<LANG>.meg`, `SFX2D_Non_Localized.meg`, `SFX3D_Non_Localized.Meg`) are opened separately by the SFX managers, not through MegaFiles.xml.

**(c) Lua loading.** Lua 5.0.2 is linked in with both parser and undumper; `lua_load` auto-detects precompiled chunks by the `\033Lua` header, so the engine accepts source **and** bytecode. Bytecode must match the VM (`virtual machine mismatch in %s: size of %s is %d but read %d` on size_t/Instruction/lua_Number) - the x64 build therefore cannot load the retail 32-bit bytecode in config.meg, and 64Patch.meg overrides them with text sources (consistent with the assets worker's finding). Scripts are resolved by name under fixed roots (`.\Data\Scripts\AI\`, `AI\SpaceMode\`, `AI\LandMode\`, `AI\StoryArc\`, `Interventions\`, `Evaluators\`, `GameObject\` + `.lua`), AI dirs are enumerated with `*.lua` (0x4e7e30); `require` uses `LUA_PATH` (default `./?.lua;./?.lc`). Errors: `LuaScript Error in %s.lua!` (0x246af2). Files are read through the MegaFile/FileClass layer, so loose `Data\Scripts` files (mods) override archived ones.

**(3) Effects.** All rendering goes through the D3DX9 Effects framework: `D3DXCreateEffectPool` (shared parameters), `D3DXCreateEffect` (from compiled .fxo in memory), `D3DXCreateEffectCompilerFromFileA` (dev path for .fx source), and a custom `ID3DXEffectStateManager` (alD3dEffectStateManager) + `ID3DXInclude` (alD3dIncludeHandler). Engine-provided parameters are bound by **semantic/annotation name** through alD3d*EngineParam classes (e.g. `_EngineParam_Get_D3d_Model_Transform`, fog, FOW texture/UV, sphere-harmonic lights `alD3dSphLightAllParam`, time, wind bend, shadow extrusion, resolution constants). A port needs: (1) an fx_2_0 bytecode -> HLSL/SPIR-V path (or the original .fx sources from the mod tools), (2) a re-implementation of the engine-param semantic table, (3) the technique/pass model (Begin/BeginPass/CommitChanges ~30M calls in the prior patch's probe CSV -> per-draw effect state is the dominant CPU render cost).

## Threading model (as shipped)

Single simulation+render thread (MainThreadClass). Extra threads only via ThreadClass (0x22e490 -> CreateThread 0x786138): LoadingThreadClass (load screen), network PacketHandler/NAT threads, BattleLoadDialog. Pools use `EmptyLockerClass` (no locks). Intel TBB is shipped but unused. So every subsystem below currently runs serially in the frame.

## File lookup priority (static answer, pass 3)

### File-open order
`FileClass::Open` (vftable slot 3, 0x2134c0) resolves a **read** request in this order. The first hit wins.
1. **Mod search list:**
   - Applies only when the path starts with `Data\`, `.\Data\`, `Data/` or `./Data/`, i.e. the case-insensitive prefix table at 0x852788.
   - `FileClass::Try_Search_Path_List` (0x214550) tries `<dir>\Data\<rest>` for each directory in the list, **in registration order**, using a direct `CreateFileA`.
   - The list is filled by `Add_Mod_Search_Path` (0x214130). It receives each `MODPATH=` argument in command-line order (from `Parse_Command_Line`, 0x67d70) and each Steam Workshop item resolved from `STEAMMOD=` (0x72210, the Steam Workshop mount), so it holds `MODPATH`/`STEAMMOD` directories. Both kinds are handled token by token, so they are **interleaved in command-line order**. A `STEAMMOD` id with no matching subscribed item mounts nothing. (corrected 2026-10-26, see PHASE2_ANSWERS Q14)
2. **Loose file relative to the working directory**, i.e. the FoC install's own `Data\...`, via `CreateFileA(name)`.
3. **Mounted MEG archives** (`MegaFileManagerClass::Open_File` 0x219ff0), newest-mounted first, as described above.
4. **Fallback tier: a CHAIN.** The first entry holding the file wins. Same prefix rule, `<dir>\Data\<rest>`.
   - Order: every `FALLBACKPATH=` directory in command-line order, then the auto-detected EaW directory (`..\GameData\`).
   - All entries live in one DynamicVector<string> (object 0x140a14ca8), and `Add_Fallback_Search_Path` (0x214110) only appends to it.
   - FALLBACKPATH entries are appended during `Parse_Command_Line` (0x67d70; call at 0x14006845f).
   - The EaW directory is appended later in boot, at 0x14005df0b (`if FALLBACK_PATH.size != 0`), after the FoC patch MEGs mount.
   - `FileClass::Try_Search_Path_List` (0x214550) iterates over every entry, and `FileClass::Open` calls it at FileClass.c step 4. See A3.

### Consequences
- **Loose files beat MEGs:** both mod-directory and base-directory loose files beat every archive, including `64Patch.meg`.
- **EaW loose files lose to FoC MEGs.**
- **Order of multiple mod paths:** with multiple `MODPATH`/`STEAMMOD`, **the earlier one on the command line wins**.
- **Mod MegaFiles.xml and Patch MEGs:** `Data\MegaFiles.xml` and `Data\Patch*.meg` are themselves opened through FileClass. A mod's own `Data\MegaFiles.xml` therefore *replaces* FoC's during mounting, and a mod's `Data\Patch.meg`/`64Patch.meg` replace the base ones, because the mod directory is checked first.
- **Write opens** skip the search lists and archives.
- **Archive-only opens:** a caller can pass an "archive only" flag (4th parameter), which skips steps 1–2 and 4.

## A3: FALLBACKPATH is a chain, not a replacement (static, settled)

Code evidence (StarWarsG.exe v1.121):
1. **The command line only appends.**
   - At 0x14006842d–0x14006845f the `FALLBACKPATH=` value is copied into a *stack* std::string (`[rsp+0x50]`) and passed to `Add_Fallback_Search_Path` (0x214110).
   - 0x214110 is a non-empty check followed by `DynamicVector_string_Add(0x140a14ca8, s)` (0x214940), which is a plain append.
   - No global is written.
2. **The GameData default is never overwritten.**
   - `FALLBACK_PATH` (std::string 0x140a15320) is written only by `Find_EaW_Fallback_Path` (0x21dce0), in three places, each logging `Setting FALLBACK_PATH to %s`: the registry ExePath, `..\..\EAW\Run\`, and `..\GameData\`.
   - Its override argument comes from global string 0x140a10d60. A scan of every RIP-relative reference finds only boot's read (0x14005da52–6e) and static init/dtor (0x1407e7677–c9), so the override is always NULL.
   - It is called unless flags 0x140a61aaa/0x140a61aab are set, and nothing in the image writes them.
3. **Both entries are searched.** Boot appends 0x140a15320 at 0x14005df0b. `Try_Search_Path_List` (0x214550) loops `i < count` and returns on the first `CreateFileA` hit.
4. **The EaW MEGs are independent of FALLBACKPATH.**
   - `<FALLBACK_PATH>\Data\MegaFiles.xml`, Patch, patch2 and 64Patch are mounted from 0x140a15320 (boot, 0x5db46 onward), i.e. always from the auto-detected EaW install.
   - This agrees with the A8 agent's reading.

The user's probe is consistent with this. With the file present in the FALLBACKPATH directory, chain and replace give the same result. Effective order, highest first:
1. MODPATH/STEAMMOD directories, earlier wins.
2. FoC loose files.
3. FoC MEGs, then EaW MEGs (later-mounted wins). Lookups ignore case and treat `/` and `\` alike, and the stored CRC is trusted.
4. FALLBACKPATH directories, in order.
5. GameData loose files.

# Build, test and gate

The full detail of building, testing and the gate. `CLAUDE.md` keeps the short rules agents must follow; everything else is here (moved verbatim on 2026-11-06 from `CLAUDE.md` "Build and test" and the build rules of "Platform and compilers", and from `docs/PHASE4.md` "Worker-count check" and "Sanitizer limits").

## Which checks a change needs (from "Platform and compilers")
- Two compilers: MSVC ships, clang checks.
- Every change: MSVC build + tests. Changes to sim code (everything in `engine/` except render, audio,
  video and UI): also the clang build + tests, including the CRC selfchecks. Changes to `engine/jobs` or
  other threading code: also `build_asan.cmd` (clang UBSan by default; `set ALAMO_SANITIZE=address` for ASan, which then runs with `-asan-stack=0` (heap and globals only) because stack instrumentation crashes catch handlers on this toolchain, see "Sanitizer limits" below; the default module list is the 11 sim modules; no TSan runtime on Windows, so races are covered by the per-worker-count CRC tests).
- Shaders are compiled by DXC (`toolchain\dxc`) to SPIR-V; the C++ compiler choice doesn't affect them.

## Build and test (moved from CLAUDE.md)
- Line endings: `.gitattributes` keeps text files LF in the working tree too (golden files and test data are compared byte for byte, so a CRLF checkout fails `alamo_ai_tests` and `alamo_shaderxlat_tests`); `.cmd` / `.bat` / `.ps1` are CRLF.
- Screenshot diffs (2026-10-30): the game smoke tests' PNGs (`build-msvc\smoke_out`, `smoke_out\screens`) are compared with 320-px-wide baselines in `tests/visual_baselines/` (about 7 MB in git). `tools\visual\visual_check.cmd` compares the last run; `run` runs the smoke tests first (needs game data and a GPU); `update` stores new baselines after an intended visual change (commit them). Mismatches get diff images in `logs\visual_diff\`. The engine is `tools/visual/png_diff.py` (`--selftest`). Not in the gate: it needs the GPU and game data.
- Generated files (Gabriel, 2026-11-07): a tool writes its output only into an ignored folder (`out/`, `work/`, `build-*`, `logs/`, or one added to `.gitignore` with the tool), never next to tracked files; about 35,000 lines of tracked generated files had to be cleaned up (roadmap groups cu17 / cu18). `tools\land_on_dev.cmd` runs `tools\lint\check_tracked.py` before it pushes, and `build_gate.cmd` runs it for the release: a file the landing adds fails when it is over 512 KiB (128 KiB for `.json` / `.csv` / `.xml` / `.txt` data outside `tests/` and `*/testdata/`), sits in an output folder, is a build product (`.obj`, `.exe`, `.log`, `.spv`, ...) or is binary outside the test-data and reference folders. Files already tracked are not checked. A file that must be tracked anyway gets a glob and a reason in `tools/lint/tracked_allow.txt`. Selftest: `check_tracked.py --selftest`.
- Version control (2026-10-30): the project is a git repository; commit before and after each agent task. Branches (2026-11-06): work goes to the long-lived `dev` branch, not a new branch per task, group or session; `main` gets `dev` by PR after `build_gate.cmd` passes on `dev` (rules in `CLAUDE.md`, "Branches"; `tools\land_on_dev.cmd` lands a session branch on `dev` safely). Build trees, logs, `toolchain/`, game data (`Data/`, `extracted/`), `re_reference/` and probe captures are ignored; `roadmap-store/` is its own repository. Remotes (both private, 2026-10-30): engine `https://github.com/Gabriel-Barney/Empire-at-war-vulkan.git` (`origin`, integration branch `dev`, released branch `main`; push after each task); roadmap store `https://github.com/Gabriel-Barney/Empire-Vulkan-Brenach.git` (`roadmap_store.py` pushes by itself after every write and build record; `python roadmap-store/roadmap_store.py sync` checks it). On a new account or machine: `git clone` the engine repo, `git clone` the store into `roadmap-store/`, then rebuild `toolchain/` with `toolchain\*.cmd` and unzip game data (these are not in git).
- Main build: run `build_msvc.cmd` from the project root. It configures `build-msvc\`
  with the local toolchain, builds everything and runs ctest. Read `logs\msvc_configure.txt` and
  `logs\msvc_build.txt`; the run is finished when `msvc_configure.txt` ends with `BUILD_DONE`.
- Every build script records its result on the roadmap (`docs/ROADMAP_PROTOCOL.md`, "Build records").
- Clang check: `build_clang.cmd` (project-local LLVM 20, MSVC ABI and headers, adds `-Wconversion -Wshadow`; logs `logs\clang_*.txt`, finished when `clang_configure.txt` ends with `BUILD_DONE`).
- One module only: add `-DALAMO_ENGINE_MODULES="core;<module>"`.
- Data-driven tests read `ALAMO_FOC_DATA` / `ALAMO_EAW_DATA` (folders containing `Data\XML`; unzip `extracted/*.zip`). They skip when unset, so a pass without them proves less. `build_msvc.cmd`, `build_clang.cmd`, `build_asan.cmd`, `build_agent.cmd` and `build_module.cmd` (the last two since 2026-11-02) call `tools\test_env.cmd`, which defaults them to `F:\SteamLibrary\steamapps\common\Star Wars Empire at War\corruption` and `...\GameData` when unset and the folder exists (2026-10-30); tests print a skip message and exit 0, so each script ends its log with `skips: data=N gpu=N other=N` from `tools\lint\ctest_skips.py` (reads ctest's JUnit file; `--list` names them). Last full run: 1 data skip (`alamo_lua_players_tests`, no PerceptualEquations folder), 0 gpu.
- Tick profiler (2026-10-30, OPT1): `alamo_headless ... --profile [--profile-out FILE] [--profile-budget MS]` prints per-tick p50/p99/max, per-zone time and the 20 worst ticks; baselines and the budget are in `docs/PERFORMANCE.md`; `bench_msvc.cmd` re-runs them. Wall-clock only: never let sim code read a profiler value.
- Scheduled gate (Gabriel, 2026-10-30: this PC runs it; on `origin/dev` since 2026-11-12): `tools\gate_scheduled.cmd [checkout]` fetches origin, forces the locked, detached worktree `.claude\worktrees\gate-dev` (made on the first run with junctions to `Data`, `extracted`, `toolchain` and `roadmap-store`; `clean_worktrees` keeps it because it is locked) to `origin/dev`, runs `build_gate.cmd` there, appends `<sha> dev gate exit N` to the main checkout's `logs\gate_history.txt` and copies the summary to `logs\gate_dev_summary.txt`. It skips with exit 3 when that `origin/dev` commit already passed, exits 4 when the setup fails, and never touches the main checkout's branch or files (before 2026-11-12 it gated whatever the main checkout had checked out and skipped on uncommitted edits, so `dev`'s tip went ungated for days). `set ALAMO_GATE_DRY=1` checks the setup without the gate. `tools\install_gate_task.cmd [HH:MM]` copies the script to `%LOCALAPPDATA%\AlamoGate\` (so a checkout never changes it while it runs) and registers that copy, with the main checkout as its argument, as the per-user nightly task `AlamoGateNightly` (default 03:00, no admin, runs while logged on; remove with `schtasks /Delete /TN AlamoGateNightly /F`). Rerun the installer after `gate_scheduled.cmd` changes.
- Landing check (2026-11-12): `tools\land_on_dev.cmd` pushes only a merged HEAD that has a passing MSVC build of every module with the fast tier or all tests. `build_agent.cmd` and `build_msvc.cmd` stamp each tree (`tools\lint\verified_build.py begin` / `pass`: HEAD, clean or not, modules, test filter; `<tree>\verified.json` only after a pass on a clean tree); `land_on_dev.cmd` accepts a `build-wt-msvc` or `build-msvc` stamp for exactly the merged HEAD, or a change to `docs/`, `*.md` or `.claude/` only, and otherwise runs `build_agent.cmd msvc wt all` itself. A pass before the merge with `origin/dev` does not count: two branches that each pass can break `dev` together. clang, ASan and slow tests stay the lane's job. Selftest: `verified_build.py --selftest`.
- String-literal pre-check (2026-11-12): `tools\lint\check_string_literals.py` finds string and character literals that do not end on their line (MSVC C2001, the most common compile error in the build records: an edit turned a `\n` escape into a real line break). `build_agent.cmd` and `build_module.cmd` run it on the C++ files changed against `origin/dev` before they build (about a second; nothing is built or recorded when it fails), and `.claude/settings.json` runs it as a PostToolUse hook on every Edit / Write of a C++ file, so the agent sees the finding at once. `--all` scans every tracked file (0 findings, about 6 s, 2026-11-12); `--selftest`.
- Pre-merge gate: `build_gate.cmd` runs the MSVC build, the clang build and `build_asan.cmd`, records each on the roadmap, prints `logs\gate_summary.txt` and exits 0 only when all three pass with 0 warnings (about 4 minutes when little has changed).
- Tests run in parallel (2026-10-30): `build_msvc.cmd` / `build_clang.cmd` use `ctest -j 8`, `build_agent.cmd` / `build_module.cmd` use `-j 4`. A full run takes about 110 s on MSVC and 100 s on clang (was about 640 s and 590 s). If you run ctest by hand, pass `-j` too and set `TMP` / `TEMP` to `<build tree>\tmp`.
- Test slots (2026-11-12): every build script runs its ctest through `tools\lint\test_slot.py`, which lets at most `ALAMO_TEST_SLOTS` (default 2) test runs go at once on this machine, across all checkouts and worktrees; a third run waits, prints who holds the slots and every 5 minutes, and runs anyway after `ALAMO_TEST_SLOT_WAIT` seconds (default 5400). Before this, about 25 sessions saw tests time out when several full runs shared the 16 cores, then pass alone. A slot is a byte lock in `%LOCALAPPDATA%\AlamoTestSlots`, dropped by Windows when its process ends, so a killed run never keeps one. `test_slot.py --status` shows the holders; `set ALAMO_TEST_SLOTS=0` turns the limit off for one shell; `--selftest`. A ctest you start by hand does not take a slot unless you prefix it the same way.
- Build state and repeat check (2026-11-13): in the build records of 2026-11-10 to 12, 92 of 359 failing test runs failed exactly the same tests as the run before in the same tree, and a record could not say which code it built. Every build script now runs `tools\lint\build_state.py begin <tree>` first: `<tree>\build_state.json` gets the commit, worktree, branch, dirty flag, a source hash (HEAD + uncommitted tracked edits + untracked files), the module list and the test filter. `build_summary.py --state <tree>\build_state.json` adds the outcome, and `record-build` copies the fields into the build record (`ALAMO_BUILD_EXTRA`; `docs/ROADMAP_PROTOCOL.md`, "Build records"). `build_agent.cmd` and `build_module.cmd` pass `--refuse-repeat`: when the last run in the tree FAILED on the same source, modules and tests, they print that run's summary again and exit 3 without building. Set `ALAMO_RERUN=1` for a flaky test or a changed environment (game data, toolchain). `build_module.cmd` now exits with the summary's code. `--selftest`.
- Golden drift in the summary (2026-11-13): `build_summary.py` splits failed tests into `real failures` and `golden drift`. A test is drift when its output shows only stored goldens that differ (`golden X: ... DIFFERS`, `FAIL golden`, a first bad checkpoint against a checked-in golden, `CRC log differs from`, `scenario changed, not comparable`) and no more failed CHECKs than goldens; a crash, timeout, a run-to-run or worker-count difference (`differs from run N`, a `_w0.crc` golden, `workers N vs 0`) is always real, and worker-count entries not run because their 0-worker setup only drifted count as drift. A run that failed only on drift ends `SUMMARY FAIL (golden drift only ...)` and still exits 1: regenerate (`tools\regen_goldens.cmd --build-dir <tree> --only all`, test-owned goldens with the test exe's `--regen`) only when the change was intended. Build records carry `failure_kind` (configure, compile, warnings, test, golden, unfinished, other), `golden_drift` and `real_failures`. Checked against 30 failing agent logs from earlier lanes. `--selftest`.
- Changed-module tests (2026-11-13): `build_agent.cmd <compiler> [tree] <modules> changed` runs only the fast-tier tests of the engine modules changed against `origin/dev` (commits, edits, untracked files; `tools\lint\changed_tests.py` maps each test to the `engine/<module>/` CMake file that registered it, so helper-made tests such as worker-count entries count for their caller). A change to `engine/CMakeLists.txt`, `engine/test_support/`, the top-level CMake or `cmake/`, or a module with no tests, runs the whole fast tier. Dependent modules' tests (apps goldens after a tactical change) are not run: use it while iterating and run the whole fast tier before landing (`land_on_dev.cmd` does it on the merged HEAD). `none` builds without tests. On 2026-11-10 to 12 the tactical movement tests alone failed in about 100 full-suite runs. `--selftest`.
- Golden-only merge conflicts (2026-11-13): when `land_on_dev.cmd`'s merge of `origin/dev` conflicts only in goldens `regen_goldens` writes (`engine/apps/headless/testdata/*.crc`, `engine/apps/game/testdata/game_smoke_*.crc` / `.rec`, `tests/benchmark/*`), `tools\lint\golden_merge.py resolve` takes `dev`'s version and commits the merge, `build_agent.cmd msvc wt all none` builds it, and `golden_merge.py regen build-wt-msvc` regenerates only those goldens (`--match` for headless ones), puts back any other golden the regen changed (the land check's fast tier then shows that drift) and commits them with a message listing each file. Any other conflicted file, a test-owned golden, a failed checkout or a failed regen stops the landing as before. `--selftest`.
- Pre-approved commands (2026-11-12): `.claude/settings.json` allows, without a prompt or an auto-mode check, `cmd /c tools\land_on_dev.cmd` (PowerShell; also `.\tools\land_on_dev.cmd`), `python -I tools/worktree/delete_merged_branch.py <claude/...> ...` (deletes remote `claude/*` branches only when their tip is in `origin/dev` or `origin/main`, and logs the SHA to `logs\deleted_branches_<date>.txt`), `python -I tools/worktree/stop_tree_procs.py [--dry-run] [build-tree ...]` (stops processes running from this checkout's own `build-*` folders, never another worktree's) and `test_slot.py --status`. Use these instead of `git push origin --delete`, `taskkill /IM alamo_*` or `Stop-Process`, which auto mode blocks ("Git Destructive", "Interfere With Workloads") because they can hit other sessions' work. Merging PRs stays blocked on purpose: `dev` -> `main` is Gabriel's call. A rule matches only the spelling written there.
- Writing tests for parallel runs: two ctest entries must not share a fixed `%TEMP%` fixture or output path, including entries that run the same exe with different arguments. Give them separate paths, or a `RESOURCE_LOCK` when they cannot be separated. Treat a flaky failure in one tree as a possible clash first.
- Long determinism tests: don't put a long run under `--check-workers`, which runs each worker count in turn inside one test. Use one ctest entry per worker count: the 0-worker entry writes the CRC log (`--crc-out`, `FIXTURES_SETUP`), the others compare against it (`--golden`, `FIXTURES_REQUIRED`). `alamo_add_worker_count_check` in `engine/CMakeLists.txt` does this; example: `alamo_headless_skirmish_ai_foc_land_outcome` in `engine/apps/CMakeLists.txt`.
- Test tiers (2026-10-31): tests that take more than a few seconds carry the ctest label `slow` (`alamo_label_slow()` in `engine/CMakeLists.txt`; today the long headless skirmish / save / galactic-AI runs, the land-outcome worker-count runs, the game smoke tests and `alamo_commands_tests` (thread-heavy scheduler test, 2026-11-01): 29 of 134). `build_agent.cmd` and `build_module.cmd` run only the fast tier (`ctest -LE slow`) by default: pass a regex to `build_agent.cmd` to run matching tests, `all` (or `set ALAMO_TESTS=all` for `build_module.cmd`) to run everything. `build_msvc.cmd`, `build_clang.cmd`, `build_asan.cmd` and the gate always run everything. Label any new test that takes more than about 5 s `slow`, together with the tests that need its fixture.
- Mod / faction name lint (modc t04, 2026-11-06): `tools\lint\check_mod_names.py` fails on a base-game or mod faction name (`tools\lint\mod_names.txt`) or a workshop id in a string literal of `engine/` sim code; an allowed use carries a `[name-ok: reason]` marker (or `[name-ok-begin: ...]` ... `[name-ok-end]`) citing the `docs/re/` spec or the task that replaces it. Runs as ctest `alamo_core_mod_names_lint` (+ `_selftest`) in every build and again in `build_gate.cmd` (`gate_summary.py` `lint` line). Rules and the audit list: `docs/status/modc-audit.md`.
- Short build output (2026-10-31): every build script ends with `tools\lint\build_summary.py` (exits, unique warnings / errors, ctest result, failed tests with the tail of their output, skips). Read that, not the whole log; `set ALAMO_FULL_LOG=1` prints the log too for `build_agent` / `build_module`. Run it by hand on any log: `python tools\lint\build_summary.py logs\msvc_configure.txt logs\msvc_build.txt`.
- Compiler cache (2026-10-31): when `toolchain\sccache\sccache.exe` exists (`toolchain\10_sccache.cmd`, pinned v0.19.0) the top-level CMake uses it as the compiler launcher and `tools\cache_env.cmd` points it at `toolchain\sccache\cache`, shared by every build tree and worktree. `-DALAMO_COMPILER_CACHE=OFF` or `set ALAMO_COMPILER_CACHE=OFF` builds without it. `build_summary.py` prints the hit / miss counts. - All modules in an agent tree: `build_agent.cmd <msvc|clang> <tree> all [tests]` configures the default `ALAMO_ENGINE_MODULES` list (`-U`, like `build_msvc.cmd`; 2026-11-07, also the `tools\pr_check.cmd` default), so nothing keeps a hand copy of the module list.

## Worker-count check (OPT3 t07, 2026-11-02)

Rule 3 says per-tick CRCs are identical for every worker count. Every OPT2 / OPT3 / CP / BM change cites this check: name the
scenario(s) it ran and the result in the PR. Two forms, both comparing every count's CRC log with the 0-worker log
(`first_divergence`, which names the first diverging tick and system):
- **Per-process (long runs), CMake** `alamo_add_worker_count_check(<name> COMMAND <exe> [args] [SETUP_ARGS ...] [CHECK_ARGS ...]
  [WORKERS ...] [TIMEOUT s] [SLOW] [PROPERTIES ...])` in `engine/CMakeLists.txt`. One ctest entry per count, so the counts run side by
  side under `ctest -j`: `<name>` runs `--workers 0 --crc-out <bin>/<name>_w0.crc` (`FIXTURES_SETUP <name>_w0`), `<name>_w1`, `_w4`, `_w16`
  and `_w<hardware threads - 1>` (`_w15` on the 16-thread reference PC) run `--workers N --golden` against it (`FIXTURES_REQUIRED`). 16 is
  more workers than logical cores here, so preemption inside a tick is covered too. `SETUP_ARGS` go to the 0-worker entry only (a
  checked-in golden, an `--expect-*` check), `CHECK_ARGS` to the others; `SLOW` labels all entries `slow`. Further entries can compare
  against the same log with `FIXTURES_REQUIRED <name>_w0` and `--golden ${<name>_CRC}`. The command needs `--workers`, `--crc-out`
  and `--golden` (every `alamo_headless` mode has them).
- **In-process (unit tests, short runs), C++** `alamo::jobs::check_worker_counts(run, counts = determinism_worker_counts())` in
  `engine/jobs/include/alamo/jobs/crc_recorder.hpp`: calls `run(workers)` (returns the run's `CrcLog`) for 0 / 1 / 4 / default and
  returns a `WorkerCountReport` (`ok()`, `first`, per-count `vs_first`). Used by `alamo_jobs_crc_tests` (incl. an injected divergence)
  and by `alamo_headless --replay --check-workers`.

Converted: `alamo_headless_replay_workers*` (per-process, the 0-worker entry also against `replay_golden.crc`; `alamo_headless_replay_golden`
now runs the in-process form) and `alamo_headless_galactic_ai_human*` (36000 ticks, was one `--check-workers` entry running the counts in
turn; each count's AI log is compared with the golden) and `alamo_headless_skirmish_ai_foc_land_outcome*` (OPT3 t08: 7000-tick land
skirmish, the 0-worker entry also checks `--expect-skirmish-base`; `_profiled` compares a `--profile` run with the same 0-worker log).
BM1 t05 (2026-11-06): `alamo_headless_bench_space_battle*` runs the check on the benchmark scenario from its save (`--bench
tests/benchmark/space_battle.abench --runs 1 --warmup 0`, slow, FoC data; docs/PHASE4.md "BM - repeatable benchmark").

## Sanitizer limits (PAF t02 / t03, 2026-10-30)

`build_asan.cmd` runs clang 20 (MSVC ABI) with UBSan by default; `ALAMO_SANITIZE=address` adds ASan.
- **ASan and exceptions.** A minimal `try { throw } catch` program built with `-fsanitize=address` crashes in the catch handler
  (static runtime: access violation inside `main` right after `CxxCallCatchBlock`; `-fms-runtime-lib=dll` does not link at all
  with this toolchain). Cause: the stack instrumentation touches the catch funclet's frame. `-mllvm -asan-stack=0` fixes it (the
  program prints and exits 0); `-asan-globals=0`, `-fsanitize-address-use-after-return=never` and `-asan-use-after-scope=0` do not.
  `build_asan.cmd` now adds `-mllvm -asan-stack=0` whenever `address` is in `ALAMO_SANITIZE`, so ASan covers heap, globals and
  use-after-free but **not stack buffer overflows or use-after-return**. The false "member call on null" at
  `engine/jobs/tests/test_jobs.cpp:196` came from the same instrumentation.
- **TSan:** no Windows runtime in LLVM 20; races are covered by the per-worker-count CRC tests.
- **Modules covered** (2026-10-30): the default is now the sim set `core;vfs;data;jobs;galactic;objects;anim;commands;tactical;lua;ai` (52 tests; UBSan 17 s, ASan about 3 min,
  both 52/52 and 0 warnings). Not covered: assets, rhi, materials, shaderxlat, terrain, render, ui, audio, video, apps (GPU / window / big-data
  tests; sim code is what the sanitizer rule protects). The first run found three real bugs, all fixed: `alamo_commands_tests` shifted a `uint32_t` by 32
  (`engine/commands/tests/test_commands.cpp`, UBSan); `alamo_tactical_abilities_tests` replaced its `CombatSystem` before its `AbilitySystem`, whose
  destructor then wrote to the freed system (test fixture order, `World::make`); `luaG_checkcode` indexed `luaP_opmodes` with an opcode
  from a corrupt save (patch in `engine/lua/CMakeLists.txt`, the save is now rejected).

## Test thread pools under a loaded machine (2026-11-03)

`alamo_ai_tactical_tests` (2 s) ran past ctest's 600 s timeout at 100% CPU. Not a deadlock: it finished once the load went.
Its `make_thread_pf` spawned and joined fresh `std::thread`s on every call, and the zone all-pairs (Floyd-Warshall) makes one
call per k, about 9300 over the shipped maps; each join waited for the new threads to get a time slice. Reproduced with 48
busy-loop processes on the 16 cores: still running at 150 s (`alamo_ai_tactical_perception_tests`, same helper: still
running at 120 s). Fix: a persistent pool whose caller claims chunks too and waits only for chunks a thread has claimed,
never for a worker to wake. Same load: 15 s and 7 s. Since CU4 (2026-11-07) that pool is the only test ParallelFor:
`engine/test_support/include/alamo/test/thread_parallel_for.hpp` (`alamo::test::make_thread_parallel_for`), used by the
galactic, tactical (+ abilities, combat, movement), ai and ai/tactical tests; the galactic / tactical copies (which waited for
every worker to report back) and the per-call spawning helpers are gone.

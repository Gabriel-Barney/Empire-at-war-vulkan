## BM - repeatable benchmark (BM1, 2026-11-06)

One shared measuring tool for every performance goal: the same game time on every run, and per-tick CRCs that prove each run
did the same work. AI actions are not in the order stream, so the AI must rerun identically from the save; the CRC proves it did.

**Scenario file** (`engine/apps/sim/include/alamo/sim/bench_scenario.hpp`, in `alamo_sim` so `alamo_game` can load the same
scenarios in BM2). A text manifest `<name>.abench` (LF, `key value` lines) next to three files it names:

| Key | Meaning |
|---|---|
| `ALAMO_BENCH 1` | format line; a reader refuses any other format |
| `name`, `version`, `description` | `version` is the scenario version: `--bench-make` keeps it when the remade files are identical and bumps it otherwise; results of different versions are never compared |
| `make <args>` | the `alamo_headless` arguments that made it (`--bench-regen` re-runs them) |
| `save <file> <bytes> <digest>` | the N1 save the run starts from (FNV-1a 64 of the bytes) |
| `orders <file> <bytes> <digest>` | the recorded order stream continuing the save (`from_save`), or `-` |
| `fingerprint <file> <bytes> <digest>` | the expected CRC log from the save tick on (`ALAMO_CRC` 1, or 2 when `fingerprint_every` > 1) |
| `fingerprint_every <N>` | 1 = every tick stored; N = a checkpoint log (every Nth tick, first and last) |
| `start_tick`, `ticks`, `workers` | the save's tick, ticks per run, default workers (`auto` = machine default) |
| `final_crc` | combined CRC after the last tick |

Every pinned file is checked against its size and digest before any timing, so a file changed without remaking the scenario
is caught. The make is deterministic: remaking with nothing changed gives byte-identical files (the test checks it). The save
leaves out the machine's game-data folder (the descriptor's informational `data_root`), so a remake on another machine keeps the
version. All files are written as temporaries and moved in place with the manifest last.

**Commands** (`engine/apps/headless/bench_run.hpp`):
- `alamo_headless --bench S.abench [--runs 3] [--warmup 1] [--workers N] [--ticks K] [--bench-json F|-] [--bench-baseline OLD.json]`:
  sim-only mode. Each run loads the save into a fresh session, replays the orders and runs the ticks as fast as possible (no
  rendering, no pacing). Each tick is timed around `SimHost::tick_once` + the harness step; OPT1's zones are recorded during the timed
  runs. Prints median / p99 (nearest rank) / worst tick per run and over all timed ticks, and the top zones. Every run's CRCs are
  compared with the fingerprint, with run 0, and with `--golden` if given. `tools\benchmark\run_bench.cmd [name]` runs it and writes
  `logs\bench_<name>.json`.
- `--bench-make S.abench --save-session KIND [...] --bench-save-at T --ticks K [--bench-every N] [--bench-desc TEXT]`: builds the
  session (the `--save-session` kinds), saves at T, loads and runs K ticks recording the orders, loads again replaying them and requires
  the same CRCs, which become the fingerprint.
- `--bench-regen S.abench` (`tools\benchmark\regen_scenario.cmd [name]`): remakes it with the recorded `make` arguments.

**Not comparable.** A fingerprint mismatch, a pinned file that differs, or a save that no longer loads prints
`scenario changed, not comparable: <first diverging tick and system>` and exits 3 (0 with `--bench-allow-changed`); the timings are
still printed but labelled, the JSON says `"comparable": false`, and `--bench-baseline` reports no speedup or slowdown for it. Two
results compare only when both matched the same scenario name, version, fingerprint digest and tick count
(`alamo::sim::bench::compare`); a different CPU, compiler, worker count or a noisy side is printed as a note.

**Busy machine.** Each run samples the machine's and the process's CPU time (`GetSystemTimes` / `GetProcessTimes`): when other
processes take more than 10 % of the CPU during a timed run the run and the result are flagged `noisy`. The first space-battle try ran
while other lanes built and tested (CPU at 100 %): the same 1800 ticks took 4.7 s in one run and 161 s in another. Benchmark on an idle
machine.

**JSON result** (`format: alamo-bench-result`, version 1): `scenario` (name, version, session, start tick, ticks, save and fingerprint
digests), `fingerprint` (ok, message), `comparable`, `settings` (ticks, workers requested / used, warm-up and timed runs, rendering off,
pacing, profiler zones), `machine` (CPU, logical cores, memory, OS build, GPU, GPU memory, GPU driver, `gpu_used: false` in sim-only
mode), `build` (compiler, config, git commit at configure time, asserts), `summary` (median / p99 / worst + its tick and run, mean,
ticks per second, `max_other_cpu_pct`, `noisy`), `runs` (the same per run plus load time, wall time, fingerprint, other CPU, final CRC),
`zones` (top 24 OPT1 zones: share, mean, p50, p99, max) and `baseline` (comparable, ratios or the reason, notes). Shared code for
BM2: `bench_stats.hpp` (median / p99 / worst, `compare`) and `bench_json.hpp` (the JSON value, write and read).

**First scenario** `tests/benchmark/space_battle.abench`: `--save-session skirmish --campaign foc-fleet` = the `--skirmish-ai foc` space battle
on `_MP_SPACE_KUAT` with both fleets four times over (20 ships a side: Empire 4 x {Star Destroyer, 2 Tartan, Acclamator, Broadside},
Rebel 4 x {Mon Calamari, Nebulon-B, 2 Corellian Corvette, Assault Frigate}; ships over the unit cap arrive as reinforcements), saved at tick 300 with
the battle running, then 1800 ticks (1 min) of AI-vs-AI battle, which does not end within them. No recorded orders (AI only).
Fingerprint every 16th tick (29 KB; every tick would be 453 KB in the repository): a divergence stays in the state, so it is caught
at the next stored tick, and `first_divergence` names the 16-tick window. Needs `ALAMO_FOC_DATA` (skipped without it).

**Tests.** `alamo_sim_bench_tests` (manifest round trip and errors, pins, statistics, the comparison rule, JSON);
`alamo_headless_bench_synthetic` (`headless/check_bench.cmake`, ~1-3 s, no game data: make a synthetic scenario, bench it with JSON,
remake it unchanged (make line with a quoted `=` argument), compare with a baseline, run 100 of 150 ticks against a
checkpoint fingerprint, reject `--ticks 0`, and refuse a scenario with another run's fingerprint and an edited sidecar as "not
comparable"); `alamo_headless_bench_space_battle*` (slow, FoC data): the OPT3 t07 worker-count check on the space battle from its save
(0 / 1 / 4 / 16 / machine default; `--bench-allow-changed`, so a sim behaviour change only prints "scenario changed" there - remake the
scenario with `tools\benchmark\regen_scenario.cmd` and commit it with the change).

### BM2 - rendered benchmark runs (2026-11-06, group bm2)

**Scenario format 2** (`bench_scenario.hpp`; BM1's format-1 files read unchanged, and a manifest with no format-2 key is still
written as format 1 byte for byte, so `space_battle.abench` and `--bench-regen` are unaffected). After `final_crc`:
`host headless|game` (whose session the save is), `mode realtime|fixed` (default fixed), `preset NAME`, `frames_per_tick K`,
`camera_anchor world|start`, and any number of `camera <tick> <tx> <ty> <tz> <yaw> <pitch> <distance> [<fov>]` keys (ticks
strictly increasing; degrees; yaw about +Z, 0 = camera on +X, not wrapped; pitch -89..89; fov 0 or left out = the view's own).
Floats are written shortest round-trip (`std::to_chars`) and read with `std::from_chars`. A remake keeps the format-2 keys; a
changed camera or setting bumps the version (`same_content` includes them), so results of two camera paths are never compared.
A *recipe* is a manifest with only name / description / format-2 keys (`Scenario::parse_recipe`).

**Camera path** (t02): `camera_pose(keys, camera_time(ticks run, alpha))`, where `camera_time` = 0 before the first measured tick,
else ticks run since the measurement started - 1 + the frame's render alpha (fixed frames: (sub + 1) / K; real time: the live
interpolation alpha). Linear between keys in double (no FMA), held outside them; the fov is linear only when both keys give one.
Never wall-clock time. In alamo_game the pose replaces the drawn view's camera (after the cinematic camera) from the first
gameplay frame on, warm-up included, so the settle check covers the path's first view; it drives the view (galactic or battle)
shown at that first frame, the other view keeps its own camera. `camera_anchor start` adds that view's own camera target at that
frame to every key's target (in fixed frames the presentation clock is frozen during the warm-up, so the anchor is the same
every run).

**alamo_game** (t01, t07; `benchmark_scenario.hpp`): `--bench-scenario S.abench` reads the manifest before the other flags
(which then win: `--benchmark`, `--bench-preset`, `--bench-ticks` up to the scenario's, `--bench-frames-per-tick`,
`--width` / `--height`), checks every pin, loads the save with the recorded orders as the session's replay (`load_game(...,
&replay)`; the run's own commands such as the autopilot's battle choice are ignored by the pipeline: the stream has them at
the same ticks; `crc_check` replays the same stream) and at the end compares the CRC log with the fingerprint (both cut at the
last fingerprint record at or before the end tick): a mismatch is `scenario changed, not comparable` (exit 3, as alamo_headless).
BM2a's named presets stay the default and the override. `--bench-make S.abench --bench-save FILE`: a normal benchmark run; when
it passes with the presentation check matching, it writes S as a `host game` scenario next to `<name>.alsv` (the save's bytes),
`<name>.acmd` (the run's recorded stream, continuing the save) and `<name>.crc` (the run's CRC log, checkpointed every 16 ticks)
with the run's mode / preset / frames per tick / ticks and the existing file's name, description, camera and version (kept when
nothing changed, else +1). The measurement must start at the save's tick (the sim holds during the warm-up).
**Finding: alamo_game cannot run BM1's `space_battle.abench`.** Its save is an alamo_headless `--save-session skirmish` harness
session (descriptor kind `skirmish`, headless participants), not an alamo_game `game.campaign` / `game.skirmish` session, so
`GameSession::spec_from_save` refuses it and the battle could not be drawn through `CampaignBattles` / the battle view anyway. Both
programs now refuse the other's scenarios with the reason before anything loads (`host` key; alamo_headless `--bench` /
`--bench-regen` exit 2 on `host game`). A large game-made space battle scenario is follow-up work.

**GPU timers** (t06): in a benchmark run alamo_game records an `rhi::GpuTimer` per frame: `frame` (the whole command buffer:
world, HUD, gamma, present blit) and the renderer's own scopes (`world`, `scene`, `ao`, `post`, `taa`). A slot's results are
read when FrameRing hands the slot out again (that frame has finished) and kept only when that frame counted; the frames still
in flight are read after a `wait_idle` at the end. Report keys (after `screen`): `scenario`, `scenario_version`, `fingerprint`,
`scenario_made`, `camera_keys`, `gpu_timestamps` (false when the queue has none), `gpu_frames`, `gpu_ms` (per scope: count /
mean / median / p99 / worst / total, GPU ms).

**Tests**: `alamo_sim_bench_tests` (format 2 round trip, format 1 unchanged, bad keys, recipes, camera interpolation),

The headless scenes run with `alamo_headless --bench tests/benchmark/<name>.abench` (BM1; `tools\benchmark\run_bench.cmd <name>`), the
rendered ones with `alamo_game --hidden --bench-scenario tests/benchmark/<name>.abench` (BM2; add `--bench-report FILE`).

**Why the rendered scenes are game-made.** `alamo_game` cannot load an `alamo_headless` harness save, and a game save of the attract
demo cannot be made, so the rendered scenes start from a *skirmish session built by alamo_game's own `GameSession`*:
`alamo_game --bench-new-save FILE --bench-map MAP [--bench-human F] [--bench-ai F] [--bench-scale N] [--bench-save-after T]
[--bench-seed S]` (no window, no GPU: `benchmark_save.hpp`) starts the skirmish (the human side's default fleet or army repeated
N times against the AI's, N 1..16), runs it until the battle is on the mode stack plus T ticks and writes the save. The human side takes
no orders in a benchmark (it only defends; the AI side attacks and keeps reinforcing). The descriptor's game-data folder is cleared and
the save has no wall-clock time, so the same arguments make the same bytes on any machine. `alamo_game --bench-maps` lists the
official skirmish maps with what a scene needs to pick one (space / land, grid, water type / height / share of vertices under it,
reflection and refraction settings, sky domes, weather, and the positions of placed nebula / cloud / field objects); `--bench-trace N`
(a benchmark run) prints every Nth tick each owner's object count, centroid and bounding box, which is how the camera paths were
aimed.

**A game scenario's recipe is its manifest**: the committed `.abench` carries a `make` line (the `--bench-new-save` arguments minus the
output) plus the format-2 keys (`host game`, `mode`, `preset`, `frames_per_tick`, `camera_anchor`, `camera ...`).

**Regenerate** (after a save-format, sim-behaviour or game-data change: "scenario changed, not comparable", exit 3):
`alamo_game --hidden --bench-regen tests/benchmark/<name>.abench` remakes the session from the `make` line, runs
`--bench-make` on it and bumps `version` when the files changed (headless scenes: `tools\benchmark\regen_scenario.cmd <name>`).
`tools\regen_goldens.cmd --bench-check` checks **every** scene with `alamo_headless --bench --runs 1 --warmup 0` (game ones sim-only
since bm2d t02; a game scene whose save no longer loads exits 3, not comparable, bm2d t01) and `tools\regen_goldens.cmd --only bench`
remakes the stale ones (game ones with `alamo_game --hidden --bench-regen`); never by hand.
New scene: write the recipe (a manifest with `name`, `description`, the `make` line and the format-2 keys), run
`alamo_game --hidden --bench-regen` on it (or `alamo_headless --bench-make`), commit the four files.

**Rebaseline** (a result file is a baseline for one scenario version on one PC): after an intended speed change run
`tools\benchmark\run_suite.cmd` on a quiet machine (nothing else building or testing; a run is flagged NOISY when the CPU was busy
before it), keep the JSON files under `logs\bench_suite\`, and compare against the previous ones with
`python tools\benchmark\compare_results.py BEFORE.json AFTER.json`. Record the new numbers in `PERFORMANCE.md` with the commit.
Never record a noisy run as a baseline.

**Result comparison** (t06; `tools/benchmark/compare_results.py`, self-test `test_compare_results.py`, ctest `alamo_bench_compare_tool`):
reads an `alamo-bench-result` (headless) or `alamo_game_benchmark` (game) file pair and prints metric / before / after / change / verdict
(`faster`, `SLOWER`, `same` within `--threshold` percent, default 3; headless also the biggest profiler zones; game also the GPU scopes,
the load time and the hitch count). It **refuses** (exit 2) two files of different kinds, scenario name, version, save or fingerprint
digest, a run that was not comparable with its scenario, and (game) a different mode / preset / size / frames per tick / tick count, each
with its own override (`--allow-different-scenario`, `--allow-different-settings`); a different machine or build is only a note
(`--allow-different-machine` silences it). A noisy run is marked and never counts for `--fail-slower PCT` (exit 4).

**Load scenes and first-use hitches** (t04): a rendered run now reports `load_ms` (from the save's load start to the first measured
tick: the load screen, warm-up frames and every pipeline / model / texture the first view waits for), `early_ms` (statistics of the
first 300 counted frames) and `hitches` (counted frames over max(25 ms, 4 x the median): their count and the worst eight as
`[frame index, ms]`). `tools\benchmark\run_suite.cmd --load` runs the rendered scenes in real time (`--benchmark realtime
--bench-ticks 300`) with a cold cache (a fresh empty `--cache-dir`: pipelines and shaders compile during the run) and then a warm one
(the same directory again); the pairs show the cold-cache hitches. In fixed-frames runs the clock waits for the renderer to settle, so
hitches only show in real-time mode.

**Noise** (t05; `tools\benchmark\run_suite.cmd [--repeats N] [--scenes a,b]`): each scene N times as separate processes; per headline
metric the min / max / mean, spread ((max - min) / mean) and coefficient of variation go to `logs\bench_suite\suite.json` and the
console. See `PERFORMANCE.md` for the figures on the reference PC.

**Tests**: `alamo_game_benchmark_tests` (extended: report keys `load_ms` / `early_ms` / `hitches`, hitch detection, the
`--bench-new-save` / `--bench-maps` flags), `alamo_bench_compare_tool` (compare tool on synthetic files, no data),
`alamo_headless_bench_galactic_late*` and `alamo_headless_bench_land_battle*` (slow, FoC data: CRCs of 1 / 4 / N workers equal the 0-worker
run), `alamo_game_bench_scene_<name>` (slow, FoC data, `bench_scene_check.cmake`: 120 hidden ticks per rendered scene, fingerprint match,
report keys).
